# End-to-End Encryption Testing Guide — Full Trace & Step Tracker

## Overview

This guide is the **test-and-track companion** for the chat app's end-to-end encryption. It walks you through the **complete E2EE lifecycle — from signup all the way to sending an encrypted message** — and, at every step, tells you exactly what to observe and check so you can **verify and track each stage of the encryption process**.

For each step you will check four things:
1. **UI action** — what you click/type in the browser.
2. **Console log** — the `[E2EE-*]` log prefix/event you should see in DevTools.
3. **Network call** — the request the client makes to the backend.
4. **State** — what is stored in IndexedDB / localStorage / the server DB.

> **Current architecture:** All message encryption uses the **Signal Protocol Double Ratchet (X3DH)** via `SessionRatchetService.ts` with Curve25519 (X25519) identity keys. There is **no legacy RSA path** — no `encryptedAesKeys`, no `UserPublicKey` table, no `/api/users/public-key`. The backend **rejects** any message where `encryptionFormat != "ratchet"` or where `ratchetHeader` is missing.

> **Current security posture (what changed in the code):**
> - **Recovery bug is FIXED.** The recovery blob now stores **both** the `curve25519PrivateKey` **and** `curve25519PublicKey`. After recovery, the local key record includes the public key, so `SessionRatchetService` **is** initialized and old messages **can** be decrypted.
> - **Identity pinning replaces raw TOFU.** `InMemorySignalStore.isTrustedIdentity()` now **rejects** a contact identity key that silently changes. Pinned identities are persisted in a new IndexedDB `identities` store. A `getSafetyNumber()` method computes a 60-bit fingerprint for out-of-band verification.
> - **Signup password is passed via `location.state`, not `window.__signupPassword`.**

## Key Inventory: All Cryptographic Keys in the System (Current)

| # | Key Type | Algorithm | Length | Generated By | Stored As | Purpose |
|---|----------|-----------|--------|-------------|-----------|---------|
| 1 | **Curve25519 (X25519) Identity Keypair** | X25519 (Signal `KeyHelper`) | 256 bits | `KeyManagementService.generateProperCurve25519KeyPair()` → `KeyHelper.generateIdentityKeyPair()` | Public: IndexedDB`curve25519PublicKey` + server `PreKeyBundle.identityKey`; Private: IndexedDB (encrypted bundle) | X3DH init + DH ratchet |
| 2 | **Signed Pre-Key (SPK)** | X25519 | 256 bits | `KeyHelper.generateSignedPreKey(identityKeyPair, id)` | Server `PreKeyBundle` + in-memory store | Medium-term DH key for X3DH |
| 3 | **One-Time Pre-Keys (OTPK)** | X25519 | 256 bits | `KeyHelper.generatePreKey(id)` (batch of 100) | Server `PreKeyBundle.oneTimePreKeys` JSON array; consumed atomically | Single-use session initiation |
| 4 | **Root Key (RK)** | X3DH (4 DH computations) | 256 bits | `SessionBuilder.processPreKey()` | In-memory session; persisted encrypted to IndexedDB | Seed for Double Ratchet derivation |
| 5 | **Chain Keys (CK)** | HKDF from RK | 256 bits | Signal ratchet | In-memory; flushed encrypted to IndexedDB | Per-message key derivation |
| 6 | **Message Keys (MK)** | HKDF from CK | 256 bits | Signal ratchet | **Deleted immediately after use** | AES-GCM per-message encrypt/decrypt |
| 7 | **Password-Derived AES Key** | PBKDF2 → AES-GCM | 256 bits | `CryptoService.deriveKeyFromPassword(password, salt)` | **Never stored** (derived on demand) | Encrypt/decrypt key bundle in IndexedDB |
| 8 | **Mnemonic-Derived AES Key** | PBKDF2 → AES-GCM | 256 bits | `RecoveryService.deriveKeyFromMnemonic(mnemonic, salt)` | **Never stored** (derived on demand) | Encrypt/decrypt recovery blob |
| 9 | **Store Encryption Key** | PBKDF2 → AES-GCM | 256 bits | `SessionRatchetService.initialize()` (from Curve25519 private key) | **Never stored** (derived on demand) | Encrypt/decrypt session data at rest |
| 10 | **DH Ratchet Ephemeral Keys** | X25519 | 256 bits | Signal ratchet per-message step | In-memory; old keys deleted after step | Forward secrecy |
| 11 | **Pinned Identity Key** (contact) | X25519 | 256 bits | Remote contact's identity public key | IndexedDB `identities` store (base64, public) | Reject silently-changed contact identities |
| 12 | **Safety Number** | SHA-256 of both identity pubkeys | 60 bits | `SessionRatchetService.getSafetyNumber()` | Displayed to user (not stored) | Out-of-band session verification |
| 13 | **JWT** | HMAC | Configurable | `TokenProvider.generateToken()` | `localStorage` | API authentication |
| 14 | **BIP39 Mnemonic** | 12-word phrase | ~108 bits (512-word subset) | `RecoveryService.generateMnemonic()` | User's memory/paper (NEVER stored digitally) | Backup key recovery |
| 15 | **PBKDF2 Salt** | Random | 128 bits | `crypto.getRandomValues()` | IndexedDB + Server `RecoveryBlob` + recovery blob | Ensure unique derived keys |
| 16 | **AES-GCM IV** | Random | 96 bits | `crypto.getRandomValues()` | IndexedDB + Server + Message payload | Ensure unique ciphertexts |
| 17 | **Key Version** | Integer | — | `KeyManagementService` | IndexedDB `keyVersion` | Track key regeneration count |
| 18 | **Device ID** | Random hex | 128 bits | `KeyStorageService.getOrCreateDeviceId()` | `localStorage("chatapp_device_id")` | Identify device for session management |

> **Note:** There is **no RSA keypair**, no `encryptedAesKeys`, and no legacy AES-wrapping in the current code.

### New Device Scenarios

| Scenario | `LoadResult` | Console |
|----------|--------------|---------|
| No local keys (cleared IndexedDB) | `{ status: "new-device", reason: "no-local-key" }` | New-device dialog appears |
| Wrong password (decrypt fails) | `{ status: "new-device", reason: "decrypt-failed" }` | New-device dialog appears |
| Recovered record | `{ status: "ok" }` (public key now present) | Ratchet initializes |

### Verification Checklist (Sign In)

- [ ] Same device + same password → loads successfully (`status: "ok"`)
- [ ] Same device + wrong password → `"new-device"` with reason `"decrypt-failed"`
- [ ] New browser (cleared IndexedDB) → `"new-device"` with reason `"no-local-key"`
- [ ] When both keys present → `SessionRatchetService.initialize` runs; persisted sessions load
- [ ] Device ID in `localStorage("chatapp_device_id")`
- [ ] Store encryption key derived and cached (not stored)

### Option A: Recovery with Phrase

### Tracking Steps (UI → Log → Network → State)

### What Happens Under the Hood

```
┌─────────────────────────────────────────────────────────────────────────────────────────────┐
│ STEP 4.2: PER-RECIPIENT DOUBLE RATCHET ENCRYPTION                                           │
├─────────────────────────────────────────────────────────────────────────────────────────────┤
│ Homepage.tsx — onSendMessage()                                                              │
│   memberIds = currentChat.users.map(u=>u.id.toString()).filter(id != self)                  │

│   )                                                                                         │
│   ratchetHeaders[recipientId] = ratchetResult.ratchetHeader  (per-recipient map)            │
│   dispatch(createMessage({                                                                  │
│       chatId: currentChat.id,                                                               │
│       content: ratchetResults[0].result.ciphertext,    // first recipient's ciphertext      │
│       iv: ratchetResults[0].result.iv,                                                     │

│        → forward secrecy: old message key deleted after use                                │
│   6. iv = crypto.getRandomValues(new Uint8Array(12))                                        │
│   7. ratchetHeader = JSON.stringify({ type, body, registrationId, deviceId })               │
│   8. await _flushSessionsToStorage()                                                        │

└─────────────────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────────────────┐
│ STEP 4.3: LAZY X3DH SESSION INIT (only when no session exists)                              │
├─────────────────────────────────────────────────────────────────────────────────────────────┤

│        → derives Root Key (RK)                                                              │

### Identity Pinning & Safety Number (TOFU replacement)

```
┌─────────────────────────────────────────────────────────────────────────────────────────────┐

## 9. Pre-Key Bundle Lifecycle

### Bundle Generation & Upload (at Signup)

```
1. VerifyOtp.tsx → KeyManagementService.uploadPreKeyBundle(token)
2. SessionRatchetService.initialize(userId, privKey, pubKey, deviceId)
3. SessionRatchetService.generatePreKeyBundle(100)
   → signed pre-key + 100 one-time pre-keys
4. SessionRatchetService.uploadPreKeyBundle(bundle, token) → PUT /api/users/pre-key-bundle
```

### Atomic One-Time Pre-Key Consumption

```
PreKeyBundleRepository.consumeOneTimePreKeyAtomic() — PostgreSQL CTE + FOR UPDATE:
  WITH popped AS (SELECT user_id, one_time_pre_keys -> -1 AS consumed_key
                  FROM pre_key_bundle
                  WHERE user_id = :userId AND jsonb_array_length(one_time_pre_keys::jsonb) > 0
                  FOR UPDATE)
  UPDATE pre_key_bundle p
  SET one_time_pre_keys = one_time_pre_keys::jsonb - -1
  FROM popped WHERE p.user_id = popped.user_id
  RETURNING popped.consumed_key::text
```
- Prevents two concurrent senders consuming the same OTPK (race condition).
- No OTPK reuse → prevents X3DH session replay.

### Automatic Replenishment

```
SessionRatchetService.refreshPreKeysIfNeeded(minCount, authToken):
  if (getOneTimePreKeyCount() < minCount) {
      newBundle = await generatePreKeyBundle(100);
      await uploadPreKeyBundle(newBundle, authToken);
  }
```
> ⚠️ Known limitation: `generatePreKeyBundle(100)` always uses IDs `1..100`. On reload, consumed OTPK IDs may be re-uploaded, weakening one-time-key guarantees.

### Signed Pre-Key Rotation (7-Day)

```
1. _getOrCreateSignedPreKeyMeta() reads localStorage 'chatapp_signed_prekey_meta' {currentId, nextRotationAt}
2. When nextRotationAt passes → rotationNeeded = true
3. _rotateSignedPreKeyMeta() → currentId = oldId + 1, fresh signed pre-key generated
> ⚠️ Known limitation: signed pre-key signature stored only in memory, lost on reload.
```

## 10. Session Persistence (Encrypted at Rest)

```
Store Encryption Key:
  Curve25519 Private Key (first 32 bytes raw)
       + salt = TextEncoder("chatapp-ratchet-store-" + userId)
       → PBKDF2(100000, SHA-256) → AES-256-GCM key

Storage:
  IndexedDB Store: ratchetSessions (keyPath: userId, e.g. "99.1")
  Value: { userId, deviceId, sessionData: AES-GCM encrypted (IV prepended), createdAt, updatedAt }

On flush (_flushSessionsToStorage):
  1. Serialize in-memory session map
  2. AES-GCM.encrypt(data, random IV)
  3. Prepend IV (12 bytes) to ciphertext, base64 encode
  4. KeyStorageService.saveSession()

MAX_SKIP = 100 (out-of-order message buffering)
```

## 11. Edge Cases

### 11.1 Pre-Key Bundle Missing (missingKeysBanner)
1. User A and User B in a chat; B never uploaded a pre-key bundle
2. A tries to send → `GET /api/users/B/pre-key-bundle` → 204
3. **Expected:** `ratchetEncrypt` throws → `missingKeysBanner` shown → message NOT sent
4. Alert auto-dismisses after 5 seconds

### 11.2 Abort During Key Regeneration (Before Phrase Confirmation)
1. Start key regeneration in Profile
2. Both uploads succeed, RecoveryPhraseDialog shows
3. Close tab WITHOUT clicking "I've Saved It"
4. **Expected:** new keys active on server; new recovery blob on server; `markPhraseShown()` NOT called
5. **Result:** user needs the new recovery phrase (if not saved → locked out)

### 11.3 Simultaneous Key Regeneration (Two Tabs)
1. Two tabs open in Profile
2. Regenerate in Tab A → completes; Regenerate in Tab B → completes
3. **Expected:** Tab B's keys are the active server bundle (last write wins); only Tab B's blob on server

### 11.4 Recovery Blob Upload Fails
1. Simulate network error on `PUT /api/recovery/blob`
2. **Expected:** full error; new pre-key bundle NOT uploaded; old keys valid; rollback restores old record

### 11.5 Pre-Key Bundle Upload Fails (Blob Succeeded)
1. Blob succeeds, simulate error on `PUT /api/users/pre-key-bundle`
2. **Expected:** full error; old bundle remains; orphaned recovery blob (no matching bundle); rollback

### 11.6 Cache Clearing (New Browser)
1. Clear site data (IndexedDB, localStorage); sign in again
2. **Expected:** "New device" dialog, reason "no-local-key"
3. **Expected:** recovery flow restores keys AND public key → old messages decrypt

### 11.7 Wrong Password on Sign In
1. Enter wrong password
2. **Expected:** "New device" dialog, reason "decrypt-failed"; IndexedDB record intact
3. User can retry or use recovery flow

### 11.8 Lazy Session Init Fails (No Pre-Key Bundle)
1. Alice ratchet-encrypts to Bob; Bob has no bundle
2. `GET /api/users/99/pre-key-bundle` → 204
3. **Expected:** error "User 99 has no pre-key bundle..."; `missingKeysBanner`; message NOT sent

### 11.9 Out-of-Order Messages (MAX_SKIP)
1. Alice sends 1, 2, 3; arrive 1, 3, 2
2. **Expected:** 1 decrypts; 3 buffers skipped chain key; 2 uses buffered key; oldest discarded after MAX_SKIP=100

### 11.10 Signed Pre-Key Rotation (7-Day Window)
1. Sign in after 7+ days
2. **Expected:** `rotationNeeded=true`; `_rotateSignedPreKeyMeta()` increments ID; fresh SPK generated

### 11.11 Two Users with Different Key Versions
1. A has keyVersion 3, B has keyVersion 1
2. **Expected:** X3DH establishes session (versions don't affect X3DH); both see plaintext

### 11.12 Password Change then Recovery
1. Change password (re-wrap); then use recovery phrase
2. **Expected:** recovery blob unchanged by password change; recovery restores ORIGINAL keys

### 11.13 Recovery Blob Fetch Returns 204
1. User navigates to `/recover` without a generated phrase
2. `GET /api/recovery/blob` → 204
3. **Expected:** error "No recovery blob found for this account..."; must use "Start fresh"

### 11.14 Identity Key Change (MITM protection)
1. User A has already pinned User B's identity key
2. Attacker substitutes a different identity key for B
3. **Expected:** `isTrustedIdentity()` returns `false` → session rejected; `saveIdentity()` refuses to overwrite
4. A safety-number mismatch is visible to the user for out-of-band comparison

> Note: `[E2EE-CRYPTO]`, `[E2EE-KEY]`, `[E2EE-RECOVERY]`, and `[E2EE] info/warn` logs are **development-only** (suppressed when `NODE_ENV=production`). Only `[E2EE]` `console.error` messages appear in production.

### What You Should NEVER See

- **`curve25519PrivateKey`** — raw private key material
- **`mnemonic`** / **`recoveryPhrase`** — recovery phrase words
- **`password`** — user password
- **`plaintext`** — decrypted message content
- **`combinedPrivateKey`** — combined JSON bundle

### IndexedDB Inspection (version 3)

1. DevTools → **Application** → **IndexedDB** → `chatapp-keystore`
2. Three object stores:
   - `privateKeys` — encrypted key bundles (keyPath: `userId`)
   - `ratchetSessions` — encrypted session data (keyPath: `userId`)
   - `identities` — pinned contact identity public keys (keyPath: `identifier`)
3. Double-click a record to inspect its fields

### localStorage Keys

| Key | Value | Set By |
|-----|-------|--------|
| `token` | JWT string | `AuthAction.ts` (signin/verifyOtp) |
| `chatapp_device_id` | Random hex string | `KeyStorageService.getOrCreateDeviceId()` |
| `chatapp_recovery_phrase_shown` | `"true"` | `RecoveryService.markPhraseShown()` |
| `chatapp_signed_prekey_meta` | `{ currentId, nextRotationAt }` JSON | `SessionRatchetService._getOrCreateSignedPreKeyMeta()` |
